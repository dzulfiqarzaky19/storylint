## Context

T-005's path-keyed exclusive chain serializes load/save/update/switchFile across every
ProjectStore instance **in one process**. The chain is a module-level Map, so a second process
has its own, and the two do not see each other.

This is a legitimate scope boundary, not an oversight: a cross-process lock is a different
design with its own failure modes (stale owners, crash recovery, timeouts). The problem is
purely that the boundary is invisible at the point where someone will hit it — running the
calm harness next to a dev server, which is what T-005's own repro does.

## Acceptance detail

- [ ] The scope limit is stated where an author hits it, not only in store.ts internals —
      at minimum in the T-005 notes and wherever the calm/dev-server workflow is documented
- [ ] Triage rule recorded: multi-process EPERM = this ticket; single-process EPERM on the
      atomic rename = T-005 regression, reopen
- [ ] If a cross-process lock is ever adopted, it is a decision record, not an inline patch,
      and it states its stale-owner policy
- [ ] NOT accepted as a fix: an EPERM retry (standing rule 11a; see T-009)

## Repro

1. Point three Node processes at one project file
2. Each performs repeated `update()` cycles
3. Observe EPERM/ENOENT (falcon measured 1 EPERM + 14 ENOENT across 3 processes)
4. Control: the same total write volume from one process → clean, because the chain applies
