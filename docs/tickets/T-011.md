## Context

The lock asserts, by regex against file text:

- `AgentPanel.tsx` calls `scrollIntoView({block:'nearest',inline:'nearest'})`
- it reads `tabRect` / `rootRect` and adjusts `scrollLeft` in both directions
- `AgentPanel.css` says `scrollbar-width: thin`, and no longer says `none`
- no `::-webkit-scrollbar { display: none }`

Those are true statements about the source. None of them renders a tab, measures a rectangle,
or could fail because a label is cut. The name promises an **outcome**; the checks establish a
**mechanism is present**.

T-010 is the proof this matters: a resting clip exists on dev right now, with this lock green.

## Two honest options

**A. Rename to match the checks.** Cheapest and fully honest:
`MUTATION lock: face-tab scroll-correction mechanism and discoverable overflow are present`.
Records what is actually protected. No new infrastructure.

**B. Add a rendered check that can fail on geometry.** Stronger, and T-010 needs one anyway —
an L1 owned-stack measurement of the resting row. If that lands under T-010, this lock can keep
a narrowed name and point at it.

Prefer A now, B via T-010. Do not do neither.

## Acceptance detail

- [ ] The test name states what the assertions can establish
- [ ] If an outcome is still claimed, a check exists that fails when the outcome is violated
- [ ] Sweep the other `MUTATION lock:` titles in the same file for the same gap — this is a
      class, not an instance (standing 12/13). Three siblings assert source text with
      outcome-shaped names; check whether they overpromise too

## Why P3

Nothing is broken by it. The lock does real work and its assertions are true. The cost is
misdirection: it already caused one real finding to be nearly dismissed as a duplicate.
