## Context

T-005 fixed Windows EPERM on the project atomic rename with a path-keyed exclusive chain
covering load/save/update/switchFile across ProjectStore instances. The chain is keyed on the
path string in a module-level Map.

That makes correctness depend on a precondition: **every path that reaches ProjectStore for a
given physical file must be the same string**. Enforced by ProjectFileRoot + ProjectStore.open.

Junction measurement is evidence that path identity ≠ file identity, not a request to support
junctions.

## Acceptance detail

- [x] A test asserts that ProjectStore path construction is single-rooted — open/switchFile
      reject outside-root paths; source scan fails on bare `new ProjectStore(` in product server files
- [x] Chosen mechanism labelled: factory + owns() runtime + source construction-site check
      (source cannot see paths laundered through helpers that still call open — owns() does)
- [x] store.ts documents the precondition next to `pathChains`: key is path string, two spellings two locks
- [x] NOT accepted: no realpath()/junction resolution in ProjectStore
