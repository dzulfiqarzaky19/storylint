## Context

T-005 fixed Windows EPERM on the project atomic rename with a path-keyed exclusive chain
covering load/save/update/switchFile across ProjectStore instances. The chain is keyed on the
path string in a module-level Map.

That makes correctness depend on a precondition nobody states in code: **every path that reaches
ProjectStore for a given physical file must be the same string**. Today that is true, because all
paths descend from one root. Nothing enforces it, and violating it does not fail — it silently
returns the defect T-005 closed.

The junction measurement below is included because it is the cheapest demonstration that path
identity and file identity are different things on this platform. It is not a request to support
junctions.

## Acceptance detail

- [ ] A test asserts that ProjectStore path construction is single-rooted — i.e. that every
      construction site derives from the same root — and fails when a construction site takes a
      path from outside that derivation
- [ ] Chosen mechanism is honestly labelled: if it is a source-level construction-site check, it
      says so and says what it cannot see (a path laundered through a helper)
- [ ] store.ts documents the precondition next to `pathChains`: the key is a path string, two
      spellings are two locks
- [ ] NOT accepted: adding realpath()/junction resolution to ProjectStore. If a future change
      genuinely needs a second root, that change owns the identity problem, and this ticket's
      test is what tells it so

## Repro

1. `mklink /J link real` over a directory containing `project.json`
2. Construct two ProjectStore instances, one per spelling, onto the one physical file
3. Observe: `resolve()` leaves the spellings distinct, lock keys differ, concurrent writes
   produce EPERM/ENOENT (falcon measured 21 errors)
4. Control: same two instances on the SAME spelling → 0 errors (the T-005 lock working)
