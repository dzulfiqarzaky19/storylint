## Context

Standing rule 11a: no EPERM retry — hiding the symptom is not a fix. It exists because a retry
turns a data-loss defect into an intermittent one, which is strictly harder to diagnose and reads
as a fix in every dashboard.

T-005 now has a real test that a failed rename does not silently succeed. It does not have, and
by its construction cannot have, a test that the failure was not retried first.

falcon shipped `e2e/proofs/t009-rule11a-no-check/probe.mjs`. This ticket wires that mechanism
into `npm test` so a retry cannot land.

## Acceptance detail

- [x] A test fails a rename ONCE and asserts the save rejects after exactly one attempt
- [x] The test asserts on observable effect (rejection + dest bytes unchanged), NOT on source text
- [x] Verified by mutation: adding a retry to saveDirect's catch makes this test fail, and the
      test passes again when the retry is removed
- [ ] If a source tripwire is added as a second layer, it is labelled a tripwire and states that
      it cannot see a differently-named helper (not added — behavioural layer is enough)
- [x] `--experimental-test-module-mocks` added to the `test` script, with its blast radius noted
      (230/230 with/without; see flag-safety.json)

## Repro

1. Insert into `saveDirect`'s catch, before `throw error`:
   `if (error.code === 'EPERM') { await sleep(50); try { await rename(temporary, path); return } catch {} }`
2. `npm test` → fully green WITHOUT the rule11a test (224/224 measured at df405c8)
3. With the wired test: same insertion fails `saveDirect does not retry a once-failed atomic rename (rule 11a)`
4. Restore → suite green again
